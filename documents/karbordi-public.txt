# Blueprint توسعه قابلیت‌های محصول در تیم کاربردی
## سطح محرمانگی: عادی
## تیم: کاربردی

### ۱. هدف
این سند استاندارد عمومی طراحی و توسعه قابلیت‌های نرم‌افزاری محصول را تعریف می‌کند. تمرکز تیم کاربردی بر تبدیل نیازهای کاربران به قابلیت‌های قابل‌استفاده، قابل‌آزمون و قابل‌نگهداری است.

استک نمونه شامل Python، FastAPI، PostgreSQL، SQLAlchemy، Pytest و Docker است. در صورت استفاده از Frontend، قرارداد ارتباط آن با Backend باید روشن و مستند باشد.

### ۲. تعریف نیازمندی
هر قابلیت پیش از پیاده‌سازی باید شامل این موارد باشد:
- مسئله‌ای که برای کاربر حل می‌شود
- رفتار مورد انتظار
- ورودی‌ها و خروجی‌ها
- شرایط خطا
- الزامات دسترس‌پذیری و تجربه کاربری
- معیارهای پذیرش
- اثر بر قابلیت‌های موجود

معیار پذیرش باید قابل‌سنجش باشد و صرفاً به عباراتی مانند «درست کار کند» محدود نشود.

### ۳. ساختار لایه‌های برنامه
- API: دریافت درخواست و برگرداندن پاسخ
- Service: اجرای منطق کاربردی و قواعد کسب‌وکار
- Repository: خواندن و نوشتن داده
- Schema: اعتبارسنجی و تعریف قرارداد داده
- Model: نمایش ساختار داده ذخیره‌شده
- Tests: بررسی رفتار مورد انتظار

قواعد کسب‌وکار نباید در چند endpoint به‌صورت تکراری پیاده‌سازی شوند.

### ۴. قواعد طراحی API
- نام endpointها باید با منابع و عملیات واقعی هماهنگ باشد.
- ورودی‌های نامعتبر باید پیش از اجرای عملیات اصلی شناسایی شوند.
- وضعیت‌های موفقیت و خطا باید قابل‌پیش‌بینی باشند.
- فهرست‌های بزرگ باید در صورت نیاز pagination داشته باشند.
- عملیات تغییردهنده داده باید در برابر درخواست‌های تکراری و رقابت هم‌زمان بررسی شوند.
- قرارداد API باید با تغییرات مهم به‌روزرسانی شود.

### ۵. مدل داده و قواعد کسب‌وکار
- محدودیت‌های داده در سطح مناسب برنامه و پایگاه داده اعمال شوند.
- فیلدهای اجباری، اختیاری و مقادیر پیش‌فرض مشخص باشند.
- قواعد محاسباتی مهم تست مستقل داشته باشند.
- رفتار حذف، بایگانی و بازیابی داده روشن باشد.
- تغییرات schema باید از طریق migration انجام شوند.

### ۶. کیفیت تجربه کاربری
- پیام خطا باید به کاربر بگوید چه اتفاقی افتاده و در صورت امکان چه کاری انجام دهد.
- وضعیت بارگذاری، موفقیت و شکست عملیات باید مشخص باشد.
- از ارسال ناخواسته چندباره فرم جلوگیری شود.
- ورودی‌ها باید به‌درستی اعتبارسنجی شوند.
- قابلیت‌های مهم باید با صفحه‌کلید و ابزارهای دسترس‌پذیری قابل‌استفاده باشند.
- رفتار رابط در حالت داده خالی و خطای شبکه تعریف شود.

### ۷. تست قابلیت‌ها
برای هر قابلیت، سناریوهای زیر بررسی شوند:
- مسیر موفق
- ورودی نامعتبر
- نبود داده
- داده تکراری
- کاربر فاقد مجوز
- خطای وابستگی
- مرزهای عددی و زمانی
- رفتار هم‌زمانی در صورت اهمیت

تست‌های واحد باید سریع باشند و تست‌های یکپارچه‌سازی محیط قابل‌کنترل داشته باشند.

### ۸. امنیت و حریم خصوصی
- داده‌های ورودی از سمت کاربر قابل‌اعتماد فرض نشوند.
- مجوز دسترسی به هر منبع در سمت سرور بررسی شود.
- داده‌های شخصی فقط به میزان لازم جمع‌آوری و نگهداری شوند.
- اطلاعات حساس در log، پیام خطا یا پاسخ غیرضروری قرار نگیرند.
- عملیات تغییردهنده داده باید از نظر دسترسی و اعتبارسنجی بررسی شوند.

### ۹. بازبینی و انتشار
پیش از ادغام:
- معیارهای پذیرش بررسی شوند.
- تست‌ها اجرا شوند.
- تغییرات API و پایگاه داده بازبینی شوند.
- خطاهای مهم و شرایط مرزی پوشش داده شوند.
- مستندات کاربر و توسعه‌دهنده به‌روز شوند.

### ۱۰. معیار تکمیل قابلیت
قابلیت زمانی آماده انتشار است که رفتار آن با معیارهای پذیرش سازگار باشد، تست‌های مرتبط موفق باشند، دسترسی‌ها صحیح باشند و راهنمای لازم برای استفاده و نگهداری موجود باشد.

### ۱۱. نگهداری
این سند استاندارد عمومی تیم کاربردی است. تصمیم‌های اختصاصی هر محصول باید در مستندات تأییدشده همان محصول ثبت شوند.
