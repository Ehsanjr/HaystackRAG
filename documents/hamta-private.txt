# Blueprint داخلی توسعه و یکپارچه‌سازی تیم همتا
## سطح محرمانگی: محرمانه
## تیم: همتا

### ۱. هدف
این سند الگوی داخلی طراحی و توسعه سرویس‌های Backend و یکپارچه‌سازی بین سامانه‌ها را تعریف می‌کند. محتوای آن باید فقط در اختیار افرادی قرار گیرد که برای انجام وظایف خود مجوز دسترسی دارند.

این سند هیچ credential، کلید واقعی، نشانی داخلی حساس یا اطلاعات دسترسی عملیاتی را نگهداری نمی‌کند. چنین اطلاعاتی باید در سامانه مدیریت اسرار مورد تأیید سازمان قرار گیرند.

### ۲. اصول معماری
- مرز مسئولیت هر سرویس باید روشن باشد.
- ارتباط میان سرویس‌ها باید قرارداد مشخص، نسخه‌بندی‌شده و قابل‌آزمون داشته باشد.
- وابستگی‌های بیرونی باید پشت interface یا adapter مناسب قرار گیرند.
- سرویس‌ها نباید بدون قرارداد مشخص به جداول داخلی یکدیگر وابسته شوند.
- تغییرات ناسازگار API باید با برنامه مهاجرت و نسخه‌بندی مدیریت شوند.
- برای عملیات حساس به تکرار درخواست، رفتار idempotent در صورت نیاز طراحی شود.

### ۳. الگوی پیاده‌سازی API
هر endpoint جدید باید این موارد را مشخص کند:
1. هدف و مالک قابلیت
2. قرارداد درخواست و پاسخ
3. الزامات احراز هویت و مجوز
4. قواعد اعتبارسنجی
5. خطاهای مورد انتظار
6. رفتار timeout و retry برای وابستگی‌های بیرونی
7. معیارهای ثبت رخداد و پایش

نمونه ساختار پاسخ خطا:

{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "منبع درخواستی پیدا نشد",
    "request_id": "example-request-id"
  }
}

پیام پاسخ نباید جزئیات داخلی، query پایگاه داده، مسیر فایل یا اطلاعات محرمانه را افشا کند.

### ۴. سیاست تراکنش و یکپارچگی داده
- مرز transaction باید متناسب با عملیات کسب‌وکار تعیین شود.
- از نگه‌داشتن transaction باز در زمان انتظار طولانی برای سرویس بیرونی خودداری شود.
- برای تغییرات چندسیستمی، تضمین‌های واقعی هر سرویس مستند شوند؛ از فرض تراکنش توزیع‌شده بدون زیرساخت مناسب پرهیز شود.
- برای انتشار رویداد پس از تغییر پایگاه داده، در صورت نیاز الگوی transactional outbox ارزیابی شود.
- سیاست retry باید خطاهای موقت را از خطاهای دائمی تفکیک کند.
- retry نباید باعث ایجاد رکورد یا عملیات تکراری شود.

### ۵. مدیریت خطا و تاب‌آوری
برای هر وابستگی بیرونی، موارد زیر مشخص شوند:
- timeout اتصال و پاسخ
- تعداد و فاصله retry
- خطاهای قابل retry
- سقف زمان کل عملیات
- رفتار در زمان از دسترس خارج شدن وابستگی
- شاخص‌های تشخیص افزایش خطا

از retry نامحدود و حلقه‌های درخواست بدون timeout اجتناب شود.

### ۶. پایگاه داده و migration
- migrationها باید قابل بازبینی و نسخه‌بندی باشند.
- تغییرات پرریسک schema باید از نظر قفل، حجم داده و زمان اجرا بررسی شوند.
- برای تغییرات ناسازگار، روش مرحله‌ای expand-and-contract بررسی شود.
- queryهای مهم از نظر execution plan و تعداد درخواست‌ها ارزیابی شوند.
- داده‌های حساس در محیط تست با داده ساختگی یا ناشناس‌سازی‌شده جایگزین شوند.

### ۷. الزامات تست
برای قابلیت‌های مهم، مجموعه تست شامل موارد زیر باشد:
- تست واحد منطق کسب‌وکار
- تست قرارداد API
- تست یکپارچه‌سازی با PostgreSQL
- تست رفتار retry و timeout
- تست مجوزدهی و دسترسی غیرمجاز
- تست جلوگیری از اجرای تکراری عملیات حساس
- تست migration در محیط آزمایشی

### ۸. ثبت رخداد و پایش
logها باید در صورت امکان شامل request ID، نام عملیات، نتیجه و مدت اجرا باشند. اطلاعات احراز هویت، tokenها، داده‌های شخصی غیرضروری و محتوای محرمانه نباید ثبت شوند.

برای سرویس‌های حیاتی، نرخ خطا، latency، تعداد درخواست و وضعیت وابستگی‌ها پایش شوند.

### ۹. فرایند انتشار
- تغییرات باید در محیط آزمایشی اعتبارسنجی شوند.
- migration و سازگاری نسخه‌های سرویس بررسی شود.
- برنامه بازگشت یا بازیابی متناسب با ریسک تغییر تعریف شود.
- انتشار باید قابلیت مشاهده و تشخیص سریع خطا داشته باشد.
- تأییدهای لازم طبق فرایند داخلی سازمان دریافت شوند.

### ۱۰. کنترل دسترسی به سند
دسترسی به این سند باید بر اساس نیاز کاری و مجوز سازمانی باشد. قرار دادن آن در مخزن عمومی، پاسخ API عمومی یا مجموعه بازیابی بدون کنترل مجوز ممنوع است.
