# Blueprint توسعه نرم‌افزار تیم همتا
## سطح محرمانگی: عادی
## تیم: همتا

### ۱. هدف و دامنه
این سند استانداردهای عمومی توسعه، نگهداری و بازبینی نرم‌افزار در تیم همتا را مشخص می‌کند. هدف، تولید نرم‌افزاری قابل‌اعتماد، قابل‌آزمون، قابل‌نگهداری و سازگار با اصول توسعه امن است.

استک مرجع این سند شامل Python، FastAPI، PostgreSQL، SQLAlchemy، Pytest و Docker است. انتخاب ابزار متفاوت باید با نیازهای فنی پروژه سازگار باشد.

### ۲. ساختار پیشنهادی پروژه

پروژه‌های Backend ترجیحاً ساختاری مشابه زیر داشته باشند:

- `src/api/`: تعریف endpointها و قراردادهای HTTP
- `src/services/`: پیاده‌سازی منطق کسب‌وکار
- `src/repositories/`: دسترسی به داده‌ها
- `src/models/`: مدل‌های پایگاه داده
- `src/schemas/`: اعتبارسنجی ورودی و خروجی
- `src/core/`: تنظیمات و قابلیت‌های مشترک
- `tests/`: تست‌های واحد و یکپارچه‌سازی

هر ماژول باید مسئولیت مشخصی داشته باشد. از ترکیب منطق HTTP، منطق کسب‌وکار و دسترسی مستقیم به پایگاه داده در یک تابع بزرگ خودداری شود.

### ۳. استانداردهای Python
- از قابلیت‌های type hint برای توابع و ساختارهای داده استفاده شود.
- نام‌گذاری متغیرها و توابع از سبک `snake_case` پیروی کند.
- نام کلاس‌ها به سبک `PascalCase` باشد.
- توابع هرچه ممکن است یک مسئولیت مشخص داشته باشند.
- از تکرار منطق مشترک در چند بخش پروژه جلوگیری شود.
- برای خطاهای قابل‌انتظار، استثناهای مشخص و قابل‌مدیریت تعریف شود.
- از ثبت اطلاعات حساس در log خودداری شود.

### ۴. استانداردهای FastAPI
- هر endpoint باید قرارداد ورودی و خروجی مشخص داشته باشد.
- ورودی‌ها با Pydantic اعتبارسنجی شوند.
- کدهای وضعیت HTTP با معنای واقعی عملیات هماهنگ باشند.
- خطاهای اعتبارسنجی و خطاهای کسب‌وکار پاسخ‌های قابل‌فهم و ساختاریافته داشته باشند.
- عملیات طولانی یا وابسته به I/O به‌درستی مدیریت شوند.
- منطق اصلی کسب‌وکار مستقیماً داخل endpoint انباشته نشود.

### ۵. استانداردهای پایگاه داده
- دسترسی به PostgreSQL از مسیر مشخص و قابل‌آزمون انجام شود.
- queryها تا حد امکان پارامتری باشند.
- تغییرات schema با migration نسخه‌بندی شوند.
- برای عملیات چندمرحله‌ای که باید یکپارچه انجام شوند، از transaction استفاده شود.
- برای جلوگیری از N+1 query، الگوی بارگذاری روابط بررسی شود.
- برای فیلدهای پرتکرار در جست‌وجو، طراحی index بر اساس الگوی واقعی مصرف انجام شود.

### ۶. تست و کنترل کیفیت
- منطق کسب‌وکار با تست واحد پوشش داده شود.
- مسیرهای مهم API با تست یکپارچه‌سازی بررسی شوند.
- برای ورودی نامعتبر، داده تکراری، رکورد ناموجود و خطاهای وابستگی تست نوشته شود.
- تست‌ها نباید به سرویس‌های خارجی واقعی وابستگی غیرضروری داشته باشند.
- تست‌های حیاتی قبل از ادغام تغییرات اجرا شوند.

### ۷. امنیت عمومی
- اعتبارسنجی ورودی در مرز سیستم انجام شود.
- احراز هویت و مجوزدهی دو موضوع جداگانه در نظر گرفته شوند.
- دسترسی به منابع باید با مجوز همان کاربر یا سرویس بررسی شود.
- رمزها، tokenها و کلیدهای API در کد منبع قرار نگیرند.
- وابستگی‌ها از نظر آسیب‌پذیری و به‌روزرسانی بررسی شوند.
- خطاهای داخلی و stack trace به کاربران نهایی نمایش داده نشوند.

### ۸. بازبینی کد
هر تغییر باید از نظر صحت عملکرد، خوانایی، تست، امنیت و اثر بر عملکرد بررسی شود. تغییرات بزرگ بهتر است به pull requestهای کوچک و قابل‌بررسی تقسیم شوند.

### ۹. معیار پذیرش
یک تغییر زمانی آماده ادغام است که:
- نیازمندی و رفتار مورد انتظار آن روشن باشد.
- تست‌های مرتبط موفق باشند.
- تغییرات API و schema مستند شده باشند.
- اطلاعات حساس در کد یا log قرار نگرفته باشد.
- حداقل یک بازبینی معتبر انجام شده باشد.

### ۱۰. نگهداری سند
این سند یک Blueprint عمومی است. قواعد پروژه‌ای خاص باید در مستندات تأییدشده همان پروژه ثبت شوند و با تغییر استک یا معماری به‌روزرسانی شوند.
